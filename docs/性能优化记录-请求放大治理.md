# 包子一哥 · 请求放大治理（性能优化记录）

> 本文档记录一次「用户请求高达 600 次/秒」的性能治理改动，供后续 review / 回退 / 交接参考。
> 日期：2026-09-04。环境：`cloud1-9gcxv3wk28637b62`（ap-shanghai）。
> 涉及云函数：`feedPosts`、`notifyMsg`（已部署生效）；涉及前端页：`pages/demo`、`pages/nearby`、`pages/mine`（已改，待重新编译）。

---

## 0. 背景与根因

**现象**：后台监控显示用户请求一度高达约 **600 次/秒**。

**诊断**（逐代码核对后确认）请求放大源不在数据量大，而在**逻辑缺陷 / 请求设计**，单用户一次操作即可放大数倍到数十倍请求：

| 放大源 | 位置 | 性质 |
|---|---|---|
| 未读数红点遍历全表 | `notifyMsg` 的 `fetchVisible` 全量分页拉取再数未读 | 无界放大，随消息量线性恶化 |
| "全部已读"逐条串行 update | `notifyMsg` 的 `actionRead(all)` 循环 `doc.update` | N 条未读 = N 次写库 |
| mine 页 onLoad + onShow 重复整套请求 | `pages/mine/mine.js` | 首次进页同一套请求打两遍 |
| 首页 demo 多类型并发 7 次 | `pages/demo/demo.js` 的 `fetchAllTypes` | 一次刷新 7 次云函数调用 |
| 附近页多类型并发 9 次 | `pages/nearby/nearby.js` 的 `fetchAllTypes` | 一次进页 9 次云函数调用 |
| feedPosts 每次 `count()` + `get()` | `feedPosts` 分页 | 每次查询 2 次数据库读 |

**结论**：这不是「真有 600 独立用户」，而是少量用户/测试脚本叠加上述放大系数打出来的。修复目标是「把每次请求降到 1 次云函数调用 + 固定次数数据库操作」，不引入 Redis（当前无必要）。

## 1. 改动清单

### 1.1 `cloudfunctions/notifyMsg/index.js`（已部署）

**改动 A：未读数改「count 差值」计算，不再遍历全表**

- 原逻辑：`fetchVisible(openid)` 全量分页拉所有可见通知，逐条数 `read_by` 不含 openid 的 → 数据库读 = 2×count + ceil(N/100)×get，**随消息量 N 无界增长**。
- 新逻辑：`unread = 可见总数(total) − 已读条数`。
  - `total` 复用列表已有的一次 count（`where(visibleCond).count()`）。
  - 已读条数 = `where(and([visibleCond, { read_by: _.all([openid]) }])).count()`。
  - 即**固定 2 次数据库读**，不随消息量增长。
  - `_.all` 对 `read_by` 字段缺失的旧数据不误判为已读（缺失 = 未读），语义与原实现一致。

**改动 B：「全部已读」改批量 update**

- 原逻辑：循环 `fetchVisible` 结果逐条 `doc.update` → N 条未读 = N 次写库（且 await 串行）。
- 新逻辑：分两段 `where().update()` 批量：
  - 段①  `read_by` 字段存在(数组) 且 未含我 → `_.push([openid])` 追加（不覆盖其他已读用户，不会重复）。
  - 段②  `read_by` 字段缺失的历史脏数据 → 整体赋值 `read_by:[openid]`（本无字段，直接建）。
  - 段①/段② 条件互斥（`exists(true)` vs `exists(false)`），marked 不重复计数。

**改动 C：删除不再被引用的 `fetchVisible` 函数。**

> ⚠️ Bug 防护要点：
> - 未读数 与 全部已读 用同一套可见语义（`visibleCond`），自洽：缺失字段=未读；段②赋值后 `_.all([openid])` 命中即转为已读。
> - 避免对「字段缺失」用 `_.push` 的不确定性 → 拆成 exists(true)+push / exists(false)+整体赋值 两段。
> - 单条已读路径（`_id`）未改动，仍用整体赋值，与 `_.all` 判定一致。

### 1.2 `cloudfunctions/feedPosts/index.js`（已部署）

**改动 A：每页去掉独立 `count()`，用 `limit(pageSize+1)` 判 hasMore**

- 原逻辑：先 `count()` 算 total（全表扫描），再 `get()` → 每次查询 2 次数据库读。
- 新逻辑：`limit(pageSize+1)`，返回条数 > pageSize 则 `hasMore=true`，展示用前 pageSize 条 → **每次查询 1 次数据库读**。
- 翻页语义不变：下一页 `skip = page*pageSize` 恰好把多取那条作为下页首条，无重复无遗漏。
- `total` 改为兼容占位：`hasMore ? -1 : (page-1)*pageSize + list.length`。已用 `findstr` 全量核对 9 个 feedPosts 消费页，前端均只消费 `list`/`hasMore`，不依赖 `total`。

**改动 B：新增 `types` 批量模式**

- 入参 `types`（字符串数组）时：一次云函数调用内部按每个 type 各取当前页并合并返回（`Promise.all` + 逐 type `where`）。
- **等价**于旧前端「对每个类型并发调一次本函数再拼接」的结果（list 顺序、hasMore=任一类型还有，均一致），但**云函数调用从 N 次降到 1 次**。
- `dataType`(单类型) / `dataTypes`(数组 `_.in` 混排) 两种旧模式**语义完全不变**，不影响招聘求职混排等既有页面。

> ⚠️ Bug 防护要点：
> - 批量用 `baseConds.concat([{data_type:tp}])`，concat 返回新数组，不污染共享的 `baseConds`。
> - 与 keyword/city/role 等通用筛选叠加均正确（批量内每 type 都带上 baseConds）。

## 4. 优化前后对比（单用户单动作）

| 场景 | 优化前 | 优化后 |
|---|---|---|
| 未读数红点查询（单次） | 2 count + ceil(N/100) get ≈ 随消息量增长 | 固定 ~2 次读 |
| 全部已读（50 条未读） | 50 次串行写 | 1~2 次批量写 |
| mine 页进页 | onLoad+onShow 各整套 ≈ 8 次云函数 | ~4 次 |
| 首页首屏刷新 | 7 次 feedPosts | 1 次 feedPosts |
| 附近页进页 | 9 次 feedPosts | 1 次 feedPosts |
| feedPosts 单次查询 | count + get = 2 次读 | 1 次读 |

综合预估：单用户请求量下降 70% 以上，且不再随消息总量线性恶化。

## 5. 遗留 / 后续建议

- 若去掉上述放大后真实峰值仍高，优先用「服务端 TTL 缓存首页全分类 feed」（非个性化热点，可用数据库集合当缓存或云函数内存缓存），**仍不建议先上 Redis**（当前无必要且引入 VPC/成本）。
- `notifyMsg`/`feedPosts` 已去掉 `count`，若后台/外部有依赖其返回的精确 `total`，需注意 `feedPosts.total` 现为占位（`-1`）。
- 其他频道页（recruit/turnover/equip/carpool/other/search）未改动，其 feedPosts 走单类型或 `dataTypes` 混排，属单次调用，非放大源；如有需要后续可同样切换 `types` 批量。
